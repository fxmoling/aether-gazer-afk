# UI Design Spec — pywebview + HTML/CSS/JS

Date: 2026-04-06
Status: Approved

## 1. Goal

Add a GUI layer (Layer 9) to the anime-game-afk project. Users can select daily tasks,
start/stop automation, and watch real-time logs — all from a lightweight desktop window.

## 2. Decisions

| Decision | Choice | Rationale |
|---|---|---|
| GUI framework | pywebview + HTML/CSS/JS | ~5MB, uses system WebView2, smallest footprint |
| Browser dependency | Edge (WebView2) | Windows 11 ships with it |
| HTTP server | None (MVP) | pywebview js_api bridge handles all communication |
| Frontend framework | None (vanilla JS) | Keeps bundle tiny, no build step |
| Theme | Dark mode only | Matches game aesthetic, no theme switching needed |
| Packaging | PyInstaller → single exe | pywebview ~5MB vs PySide6 ~120MB |

## 3. MVP Scope

Task-level control with two pages:

- **Task page** (default): 10 daily tasks with checkboxes, status indicators, start/stop,
  connection status
- **Log page**: Full-screen real-time log viewer with level filtering

Not in MVP: settings page, system tray, YAML plan editor, run history, browser fallback HTTP server.

## 4. Architecture

```
Layer 9 (new)
  ui/app.py          → pywebview window creation, entry point
  ui/api.py          → Api class exposed to JS via js_api
  ui/bridge.py       → LogForwarder: loguru sink → evaluate_js push
  ui/task_manager.py → TaskManager: task state, Pipeline orchestration
  ui/web/            → index.html, style.css, app.js

Layer 8 (existing, unchanged)
  orchestrator/      → Pipeline, ProcessRegistry, ProcessExecutor

Layer 3 (existing, unchanged)
  runtime/logger     → loguru (LogForwarder adds a sink, does not modify)
```

Dependency rule: ui/ imports from tasks (L6), knowledge (L4), ops (L5), and runtime (L3).
Nothing imports from ui/.

Note: TaskManager does NOT go through Pipeline/Orchestrator (L8) for individual task
execution. It runs selected tasks directly (like DailyRoutine does) so the UI can control
per-task start/stop and push per-task status updates. The Pipeline is designed for YAML
plan execution — the UI replaces that entry point with interactive control.

### 4.1 Communication Flow

```
JS (frontend)                    Python (backend)
─────────────                    ───────────────
await pywebview.api.get_tasks()  →  Api.get_tasks() → TaskManager._tasks
await pywebview.api.start_run()  →  Api.start_run() → TaskManager.start()
                                                       → Pipeline.run() on bg thread
                                 ←  window.evaluate_js('appendLog(...)')
                                 ←  window.evaluate_js('updateTaskStatus(...)')
```

- **JS → Python**: pywebview `js_api` — JS calls `await pywebview.api.method()`, returns JSON.
- **Python → JS**: `window.evaluate_js()` — Python pushes log entries and task status updates.
- No HTTP server, no WebSocket, no polling.

### 4.2 Threading Model

```
Main thread:     pywebview event loop (webview.start() blocks)
Worker thread:   Pipeline.run() via asyncio.run() in threading.Thread
```

- `webview.start()` blocks the main thread (required by pywebview).
- `TaskManager.start()` spawns a daemon thread that runs `asyncio.run(pipeline.run(...))`.
- `TaskManager.stop()` sets an `threading.Event` flag; Pipeline checks it between tasks.
- `window.evaluate_js()` is thread-safe in pywebview — can be called from the worker thread.
- Api methods are called from the pywebview thread — access shared state via TaskManager
  which uses a `threading.Lock` for `_tasks` and `_running` state.

## 5. Api Class Interface

```python
class Api:
    """Exposed to JavaScript via pywebview js_api."""

    # Connection
    def connect(self) -> dict
        # Returns: {"ok": bool, "resolution": str, "error": str|None}
        # Creates DeviceAdapter, calls connect(), stores in TaskManager.

    def disconnect(self) -> dict
        # Returns: {"ok": bool}

    def get_status(self) -> dict
        # Returns: {"connected": bool, "running": bool,
        #           "elapsed_s": float, "completed": int, "total": int}

    # Tasks
    def get_tasks(self) -> list[dict]
        # Returns: [{"id": "mail", "name": "领取所有邮件",
        #            "description": "Collect all mail",
        #            "enabled": True, "safe": True,
        #            "status": "pending|running|success|failed|skipped"}, ...]
        # Task list is built dynamically from _DAILY_TASKS in daily_routine.py.

    def set_task_enabled(self, task_id: str, enabled: bool) -> dict
        # Returns: {"ok": bool}
        # Persists to a local JSON config file so selections survive restart.

    def set_all_enabled(self, enabled: bool) -> dict
        # Returns: {"ok": bool}

    # Execution
    def start_run(self) -> dict
        # Returns: {"ok": bool, "error": str|None}
        # Starts Pipeline on worker thread with only enabled tasks.

    def stop_run(self) -> dict
        # Returns: {"ok": bool}
        # Signals worker thread to stop after current task completes.

    # Logs
    def get_recent_logs(self, count: int = 100) -> list[dict]
        # Returns: [{"time": "14:32:05", "level": "INFO", "message": "..."}, ...]
        # From LogForwarder ring buffer. Used on page load / page switch.
```

```python
    _window: webview.Window | None   # for evaluate_js push

    def load_tasks(self) -> None
        # Reads _DAILY_TASKS from daily_routine.py
        # Restores enabled/disabled state from config JSON

    def start(self) -> None
        # 1. Filter _tasks to only enabled ones
        # 2. Spawn worker thread running _run_tasks()
        # 3. Push status updates via evaluate_js after each task completes

    def stop(self) -> None
        # Sets _stop_event; worker thread checks between tasks

    def _run_tasks(self) -> None
        # Runs on worker thread via asyncio.run()
        # Iterates enabled tasks in order (same order as _DAILY_TASKS)
        # For each task:
        #   1. Push status "running" to frontend
        #   2. Instantiate task class, call task.execute(ctx)
        #   3. Return to hub between tasks (ReturnToHub)
        #   4. Push status "success"/"failed" to frontend
        #   5. Check _stop_event before next task
        # This mirrors DailyRoutine.execute() logic but with UI-driven
        # task selection instead of running all 10 unconditionally.

    def _push_task_status(self, task_id: str, status: str) -> None
        # thread-safe: window.evaluate_js('updateTaskStatus("mail","success")')
```

## 9. Config Persistence

Task enabled/disabled state saved to `config/ui_state.json`:

```json
{
  "tasks": {
    "mail": true,
    "intel_shards": true,
    "joint_defense": false
  },
  "window": {
    "width": 900,
    "height": 600
  }
}
```

Loaded on startup, saved on every toggle. Uses atomic write (write .tmp then os.replace)
per project coding standards.
